# M7 metrics

Real command transcripts and measured numbers for M7 (Presentation, polish,
writeup). Everything here is a real run — see CLAUDE.md's "never fabricate a
metric" rule.

## M7-1 — `core/anim/TwoBoneIk.luau`

```
lune run tests   -- tests/twoBoneIk.spec.luau
```

All five cases docs/08 §Tests names: reachable, exactly-reachable,
unreachable, degenerate coincident points, and pole-vector plane correctness.
Expected values are hand-computed from the law of cosines and verified
independently before being written down, not read back out of the module. The
3-4-5 case is used throughout because every value in it is exact in binary
floating point, so a failing assertion is a real failure rather than a
rounding artifact:

```
L1=3, L2=4, d=5  ->  along = (9 + 25 - 16) / 10 = 1.8
                     perp  = sqrt(9 - 1.8^2)    = 2.4
                     |joint-root| = 3   |target-joint| = 4
```

Design note: out-of-range targets are handled by **clamping the distance**,
not by branching. A target past `L1 + L2` clamps to exactly that, which makes
the perpendicular offset zero and straightens the limb toward the target —
docs/08's "extend straight toward it" behaviour falling out of the same
arithmetic instead of needing a separate code path. Two inputs still need
catching before the math because they make the axis undefined rather than
merely extreme: coincident root and target, and a pole vector parallel to the
axis.

## M7-2 — `core/anim/StepPlanner.luau`

```
lune run tests   -- tests/stepPlanner.spec.luau
```

The three properties docs/08 §Tests names, with the "opposing legs never lift
together" invariant checked **every frame of a simulated walk** rather than
once — a gait that alternates for one frame and then desynchronises is exactly
the bug worth catching, and only a continuous check finds it. Held across 600
frames walking straight, 600 frames of continuous direction change, 300 frames
at 80 studs/s, and 600 frames up a staircase.

### A real starvation bug the tests caught

Serving whichever leg asks first *looks* like alternation and is not. A leg
lands and, still inside the same `step()` call, is planted again and already
past the threshold, so it re-commits before any other group is considered. Its
group is then permanently in flight, the opposing gate never opens, and the
other legs never move at all.

Measured on a quadruped walking 900 frames at 6 studs/s, before the fix:

```
group1 steps: 2    group2 steps: 0
leg 2 (group 2) current.x = -1.00   body.x = 90.0    <-- 90 studs behind
leg 3 (group 2) current.x =  1.00   body.x = 90.0
```

After choosing the serving group explicitly, preferring whichever group did
not step last:

```
group1=58  group2=56  ratio=1.04   maxFootLag=3.20 studs
stairs: body.x=60.0  bodyHeight=11.60  (terrain height ~12.00)
```

Two of my own tests were wrong and were corrected rather than the code. A
completed step cannot be observed by polling for `stepPhase == 0`, because a
leg that lands can re-commit within the same call — so the test asserts what
the criterion actually claims, that the foot ends exactly on the position it
committed to. And "run 40 frames then check" was comparing against a stale
target, since a body left at the origin makes the foot correctly want to step
back.

## M7-9 — Room catalogue, 12 → 24 modules

```
lune run tests               -- 1,000-seed Assemble sweep, green
lune run tools/validate-config -- pass
```

The accept criterion (`Assemble` still passes 1,000-seed validation) holds.
The more interesting question is whether doubling the catalogue actually buys
anything, so it was measured across 400 seeds:

| Catalogue | distinct layouts | never placed | modules/layout |
|---|---:|---:|---:|
| 12 originals | 250 | 1 | 15.8 |
| **24 (shipped)** | **349** | 4 | 16.1 |
| 24, two smallest enlarged to ~2,200 studs² | 275 | 4 | 16.0 |
| 24, two smallest at ~1,300 studs² | 348 | 5 | 16.0 |

Doubling the catalogue raised distinct layouts **250 → 349, about +40%**.

### Four modules are never placed, and that is structural

`Assemble` scores candidates purely on how close their area is to the
remaining area budget divided by the remaining module count — roughly 4,250
studs² against a 68,000 target. Anything under ~2,000 studs² therefore loses
that comparison at *every* step of the walk and is never the best fit. Which
modules are dead depends only on which happen to be smallest; one module was
already dead in the 12-module catalogue before any of this.

**Resizing does not fix it, it relocates it.** Enlarging the two smallest
additions to ~2,200 studs² left the dead count at four — the next-smallest
modules simply took their place — and *cost* diversity, 349 → 275, because
mid-sized modules all compete for the same slots. The shipped configuration is
the one that measured best, and the small modules are kept at their authored
sizes deliberately.

The real fix is a variety term in the candidate score rather than pure
area-fit. That is a change to tested assembly logic and out of scope for a
catalogue task, so it is recorded here rather than attempted.

## M7-5 — Zone lighting presets, transitions, threat modulation

Verified in Studio against the running client, reading the live `Lighting`
properties rather than trusting the controller to report on itself.

Per-zone, reached through the **real** path (server sends the zone name in
`RunState`, HUD forwards it to `LookController`):

```
Perimeter   fog=180.0  tint=(0.95,0.98,1.00)  sat=-0.10  con=+0.12  bloom=0.60
Processing  fog= 90.0  tint=(1.00,0.92,0.82)  sat=-0.25  con=+0.22  bloom=1.10
Vault       fog= 45.0  tint=(0.82,0.86,1.00)  sat=-0.40  con=+0.35  bloom=1.80
```

Each matches `config/Zones` exactly. Screenshots captured at all three, plus
threat tier 1 vs 5 — the Vault is visibly cold, tight-fogged and blown out
around light sources, which is docs/08's "desaturation increasing with depth,
fog closing in, contrast rising" landing as intended.

Threat tier, measured at both extremes:

```
tier 1   fog=180.0  tint=(0.95,0.98,1.00)  sat=-0.10  bloom=0.60
tier 5   fog=144.0  tint=(1.00,0.88,0.86)  sat=+0.02  bloom=1.30
```

Fog tightens by exactly 20% (180 -> 144) and bloom rises by exactly the
documented +0.70, with the tint pushed red — the numbers docs/08 specifies,
not approximations of them.

**The transition is a blend, not a snap**, sampled every 80ms:

```
t=0.08s fog=174.0   t=0.17s fog=167.9   t=0.25s fog=161.9
t=0.33s fog=163.6   t=0.42s fog=164.4   t=0.50s fog=165.1  ...
```

The reversal at t=0.33s is the real wiring asserting itself: the ~1Hz
`RunState` push reported the player was still in the Perimeter and overrode
the injected zone. Worth keeping in the record because it is evidence of two
things at once — the end-to-end path works, and an *interrupted* transition
reverses smoothly from wherever the blend had reached rather than snapping
back to its old endpoint.

### Two ownership bugs found and fixed here

**Two writers on one property.** M4-9 drove `ColorCorrectionEffect` from
`HudController` for threat tier, and M7-5 drives the same effect from the
zone preset. Two writers means whichever tween lands last wins and the stack
flickers between answers — the exact failure `HudController's` own header
warns about. Threat tier now routes through `LookController.setThreatTier`
and is *composed* with the zone preset by `core/look/LightingBlend` instead of
fighting it. Confirmed in Studio: exactly one ColorCorrectionEffect live.

**Effects stack by class, not by name.** A first pass looked up effects by the
name this controller gives them, booted into a place that already had a
`Bloom` and an `Atmosphere`, and created a *second* BloomEffect beside the
existing one — post effects of the same class multiply, so the result matched
no preset in the config. Measured at the time: `BloomEffect x2`. Fixed by
adopting the first existing effect of the class. After: one of every class.

```
Atmosphere x1   BloomEffect x1   ColorCorrectionEffect x1
DepthOfFieldEffect x1   Sky x1   SunRaysEffect x1
```

**A gap this exposed:** nothing was calling `setZone` at all — the client had
no idea which zone it was in. `LevelService.zoneAt` (point-in-rect against the
placed modules, not nearest-centre, since modules range 32x32 to 128x96 and a
nearest-centre test flips zones while the player stands still) now resolves it
server-side, and the zone name ships in the existing `RunState` push rather
than replicating the whole layout for one string.

## M7-7 — EditableImage budget

The accept criterion is "the 9th allocation is refused cleanly, no error
thrown". Exceeding 8 live instances fails at *creation* with a memory-budget
error, so the ledger (`core/look/ImageBudget`) is pure and consulted **before**
`Instance.new` is ever called — which makes the refusal path provable in unit
tests without allocating nine real images and hoping the ninth fails.

Verified in Studio against the running controller:

```
at boot: live=3 held=[damage_state, threat_gradient, zone_palette]   (docs/08 slots 1-3)
acquire probe3      -> true   live=6
acquire probe4      -> false  live=6  reason="budget exhausted: 6 live, cap 6"
did the refusal throw?  no (correct)
reserved acquire #7 -> true   live=7
reserved acquire #8 -> true   live=8
reserved acquire #9 -> false  live=8  reason="budget exhausted: 8 live, cap 8"
final: live=8 peak=8 refusals=5 hardCap=8 normalCap=6
after releaseAll: live=0 (no leak)
```

The reserve is genuinely reserved: ordinary callers are refused at 6 while a
reserved caller can still take 7 and 8, and even a reserved caller cannot
exceed the hard cap. A leak test drives 100 acquire/release cycles of the
zone palette — the realistic failure being a zone transition that re-acquires
without releasing, which would bleed one slot per transition and throw on the
7th — and ends at `live=0, refusals=0, peak=1`.

## M7-4 — Ragdoll pool

Scheduling lives in `core/anim/RagdollPool` and is unit-tested, so pool
exhaustion — the only interesting case — is provable without instantiating a
single physics rig.

The M7-4 accept criterion, run in Studio through the real death handler:

```
before: pool size=12 active=0 spawned=0
20 deaths in 2s threw an error?  no (correct)
after:  active=12/12  spawned=20  evictions=8  visibleRigs=12
  active never exceeded pool size: true
  20 deaths, 12 slots -> expect 8 evictions: true
after 9s: active=0 recycledRigs=12 visibleRigs=0 -> recycles cleanly: true
```

**Exhaustion evicts the oldest corpse, not the newest death.** The body the
player is looking at is the one they just made; preserving a 7-second-old
corpse instead means kills stop producing bodies exactly during a firefight,
which is when the pool runs out.

Noted while testing, and **not** a bug: Studio logs `EditableImage is not
accessible. Go to the Security Tab in Experience Settings to enable this API.`
Creation still succeeds — `CreateEditableImage` returns a real object and the
budget correctly reports `imageFailures=0` holding three images. The setting
governs whether they can be *displayed*. It is a place setting only a human
can toggle, in the same family as M0-8's HTTP switch.

## M7-3 / M7-10 — LOD locomotion and the client frame profile

`core/anim/Lod` owns the tier boundaries and the raycast allocator, both pure.
The allocator matters more than it looks: the budget is a decision made once
per frame with the whole population in view, rather than a first-come race
between entities, and ties are broken by id so two entities at equal distance
cannot swap places frame to frame and alternate stale ground planes forever.

Measured in Studio, 40 spawned entities, sampled over 241 real frames:

```
LOD census:   full=32  reduced=0  clip=0  culled=0   (32 = INTEREST_MAX)
raycast budget    24 / frame
peak observed     24
within budget     true
interpolation + transforms   0.080 ms   (docs/08 budget 1.5 ms)
procedural animation + IK    0.439 ms   (docs/08 budget 2.0 ms)
```

The first sample had every entity in the `full` band because Skitters chase
the player and had closed the distance. Pulling the *camera* back instead —
which is what LOD keys off anyway, and avoids tripping the movement guard —
exercises all four bands with real distances:

| camera back | full | reduced | clip | culled | raycast peak | anim cost |
|---:|---:|---:|---:|---:|---:|---:|
| 20 studs | 40 | 0 | 0 | 0 | **24 / 24** | 0.572 ms |
| 60 studs | 0 | 40 | 0 | 0 | 0 / 24 | 0.269 ms |
| 110 studs | 0 | 0 | 40 | 0 | 0 / 24 | 0.003 ms |
| 200 studs | 0 | 0 | 0 | 40 | 0 / 24 | 0.003 ms |

Two things this shows that the unit tests cannot: raycasts occur **only** at
the `full` tier (zero at every other band, exactly as docs/08 specifies), and
the cost falls monotonically as the population moves outward — 0.572 → 0.269 →
0.003 ms. The raycast counter never exceeded 24 in any configuration, which is
the M7-3 accept criterion.

Against docs/08's per-frame budget table, at 40 entities:

| System | Budget | Measured |
|---|---:|---:|
| Entity interpolation + transform writes | 1.5 ms | **0.080 ms** |
| Procedural animation + IK (LOD'd) | 2.0 ms | **0.439 ms** |
| Leg raycasts (capped at 24) | 0.8 ms | included in the animation figure |

Both are comfortably inside budget. The raycast cost is not separated out
because the rays are issued from inside the gait's `groundAt` callback, so
timing them separately would mean instrumenting a closure called per leg per
entity — cost that would distort the very number being measured.

### Honest limitation on M7-3

The gait and IK are computed, LOD'd and budgeted, and the *scheduling* half of
the criterion ("raycast counter never exceeds 24") is verified. The other half
— "no popping at LOD transitions" — is **not** meaningfully verifiable yet,
because entities currently render as a single box part: there is no limb
geometry for the solved joint positions to drive, so there is nothing visual
to pop. `TwoBoneIk.solve` is called per leg and its cost is in the numbers
above, but its result is not yet written to any visible part. Authoring
per-kind rigs is asset work that belongs with M7-6/M7-8, and claiming the
visual criterion before those exist would be claiming something untested.
