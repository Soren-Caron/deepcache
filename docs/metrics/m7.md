# M7 metrics

Real command transcripts and measured numbers for M7 (Presentation, polish,
writeup). Everything here is a real run — see CLAUDE.md's "never fabricate a
metric" rule.

## M7-1 — `core/anim/TwoBoneIk.luau`

```
lune run tests   -- tests/twoBoneIk.spec.luau
```

All five cases docs/08 §Tests names: reachable, exactly-reachable,
unreachable, degenerate coincident points, and pole-vector plane correctness.
Expected values are hand-computed from the law of cosines and verified
independently before being written down, not read back out of the module. The
3-4-5 case is used throughout because every value in it is exact in binary
floating point, so a failing assertion is a real failure rather than a
rounding artifact:

```
L1=3, L2=4, d=5  ->  along = (9 + 25 - 16) / 10 = 1.8
                     perp  = sqrt(9 - 1.8^2)    = 2.4
                     |joint-root| = 3   |target-joint| = 4
```

Design note: out-of-range targets are handled by **clamping the distance**,
not by branching. A target past `L1 + L2` clamps to exactly that, which makes
the perpendicular offset zero and straightens the limb toward the target —
docs/08's "extend straight toward it" behaviour falling out of the same
arithmetic instead of needing a separate code path. Two inputs still need
catching before the math because they make the axis undefined rather than
merely extreme: coincident root and target, and a pole vector parallel to the
axis.

## M7-2 — `core/anim/StepPlanner.luau`

```
lune run tests   -- tests/stepPlanner.spec.luau
```

The three properties docs/08 §Tests names, with the "opposing legs never lift
together" invariant checked **every frame of a simulated walk** rather than
once — a gait that alternates for one frame and then desynchronises is exactly
the bug worth catching, and only a continuous check finds it. Held across 600
frames walking straight, 600 frames of continuous direction change, 300 frames
at 80 studs/s, and 600 frames up a staircase.

### A real starvation bug the tests caught

Serving whichever leg asks first *looks* like alternation and is not. A leg
lands and, still inside the same `step()` call, is planted again and already
past the threshold, so it re-commits before any other group is considered. Its
group is then permanently in flight, the opposing gate never opens, and the
other legs never move at all.

Measured on a quadruped walking 900 frames at 6 studs/s, before the fix:

```
group1 steps: 2    group2 steps: 0
leg 2 (group 2) current.x = -1.00   body.x = 90.0    <-- 90 studs behind
leg 3 (group 2) current.x =  1.00   body.x = 90.0
```

After choosing the serving group explicitly, preferring whichever group did
not step last:

```
group1=58  group2=56  ratio=1.04   maxFootLag=3.20 studs
stairs: body.x=60.0  bodyHeight=11.60  (terrain height ~12.00)
```

Two of my own tests were wrong and were corrected rather than the code. A
completed step cannot be observed by polling for `stepPhase == 0`, because a
leg that lands can re-commit within the same call — so the test asserts what
the criterion actually claims, that the foot ends exactly on the position it
committed to. And "run 40 frames then check" was comparing against a stale
target, since a body left at the origin makes the foot correctly want to step
back.

## M7-9 — Room catalogue, 12 → 24 modules

```
lune run tests               -- 1,000-seed Assemble sweep, green
lune run tools/validate-config -- pass
```

The accept criterion (`Assemble` still passes 1,000-seed validation) holds.
The more interesting question is whether doubling the catalogue actually buys
anything, so it was measured across 400 seeds:

| Catalogue | distinct layouts | never placed | modules/layout |
|---|---:|---:|---:|
| 12 originals | 250 | 1 | 15.8 |
| **24 (shipped)** | **349** | 4 | 16.1 |
| 24, two smallest enlarged to ~2,200 studs² | 275 | 4 | 16.0 |
| 24, two smallest at ~1,300 studs² | 348 | 5 | 16.0 |

Doubling the catalogue raised distinct layouts **250 → 349, about +40%**.

### Four modules are never placed, and that is structural

`Assemble` scores candidates purely on how close their area is to the
remaining area budget divided by the remaining module count — roughly 4,250
studs² against a 68,000 target. Anything under ~2,000 studs² therefore loses
that comparison at *every* step of the walk and is never the best fit. Which
modules are dead depends only on which happen to be smallest; one module was
already dead in the 12-module catalogue before any of this.

**Resizing does not fix it, it relocates it.** Enlarging the two smallest
additions to ~2,200 studs² left the dead count at four — the next-smallest
modules simply took their place — and *cost* diversity, 349 → 275, because
mid-sized modules all compete for the same slots. The shipped configuration is
the one that measured best, and the small modules are kept at their authored
sizes deliberately.

The real fix is a variety term in the candidate score rather than pure
area-fit. That is a change to tested assembly logic and out of scope for a
catalogue task, so it is recorded here rather than attempted.
