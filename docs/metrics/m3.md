### A real bug, found by running it rather than reading it

The first invocation rejected **4781 of 6075 lines (79%)**. The instinct was
to suspect the envelope shape, so that was checked first — every line passed
`backend/src/ingest/validate.ts`'s real validator when run directly, no
mock. The actual cause was in the simulator's batching: it accumulated
events from a pool of 40 simulated `serverId`s into one HTTP POST for
throughput, and `/v1/ingest` correctly rejects any line in a batch that does
not share the first line's `serverId` — a real game server only ever flushes
its own buffer, so a batch spanning servers is not a shape the endpoint is
meant to accept. Fixed by assigning every run to a server before generating
anything, and flushing per server rather than per byte budget. The second run
above is the fixed version; the rejection count is not an artifact of a
smaller or easier test — it is the same 2000-run, 30-day generation that
failed 79% of the time before the fix.

## Failure drill (M3-8)

The real backend process, killed for real — not a simulated outage.

```
BASELINE (backend up)
run: elapsed=11 active=1 complete=false
tick: p95=0.13ms overruns=0 ticks=219

[backend process killed; /healthz confirmed unreachable]

emitted 1500 synthetic events        <- forces past the 1000-capacity ring
DURING OUTAGE
run: elapsed=30 active=1 complete=false
tick: p95=0.12ms overruns=0 ticks=593
telemetry: queued=801 seq=1502 dropped=500 droppedSinceFlush=500
```

**Gameplay is genuinely unaffected**, not just "should be" per the design:
tick p95 held at 0.12ms with 0 overruns while 1500 events were pushed against
a dead backend, and the run clock advanced 19 real seconds exactly as it
would have with the backend healthy.

```
[backend restarted; /readyz -> {"status":"ready","checks":{"database":"ok"}}]

RECOVERY
flush landed=true
after: queued=800 posted=201 dropped=503 droppedSinceFlush=0

SELECT type, payload FROM events WHERE type = 'telemetry.dropped'
ORDER BY ingested_at DESC LIMIT 1;

 telemetry.dropped | {"count": 503}
```

**The drop counter rides the next successful batch with the real count**,
landing as an ordinary row in the same `events` table everything else uses —
no separate reporting path to keep in sync.

**Found while running the drill:** a successful flush left the previous
outage's error message in place. `TelemetryService.describe()` reported
`lastError = HttpError: ConnectFail` even immediately after a flush had
landed cleanly — a dashboard reading this mid-recovery would show a live
incident that had already ended. Fixed: `flushOnce` clears `lastError` on the
success path. Verified directly — forced a failure, confirmed the error was
set, forced a success, confirmed it read back as an empty string.

### A real bug this caught: `.env` was never being read

`backend/.env` existed, with a secret matching
`src/server/config/Backend.luau`. Nothing in the repository actually loaded
it — no `dotenv` import anywhere. The backend was booting on its own built-in
fallback secret (`dev-insecure-ingest-secret`), which did not match the
game's, so **every signed batch was failing verification**, and the failure
presented as `HttpError: ConnectFail` / a breaker opening — indistinguishable
from a genuinely unreachable backend. This is the exact failure mode the
HMAC module's own comments warn about: a signature mismatch that looks like a
network problem instead of an auth bug.

Root-caused by checking, directly, what secret a fresh process actually
loaded:

```
npx tsx -e "loadConfig().ingestSecret"
"dev-insecure-ingest-secret"          <- before the fix, wrong
"dev-ingest-secret-change-me"         <- after adding dotenv, matches Backend.luau
```

Fixed by loading `dotenv` once in `config.ts` rather than requiring every
entry point to remember it. Verified by the live-session flush above landing
with `dropped=0` immediately after the fix. For comparison, `tasks/BACKLOG.md`'s
M3-2 entry records what a *genuinely* unreachable backend looks like from the
same diagnostics bridge — `HttpError: ConnectFail`, failures climbing 2 → 3,
the breaker opening for 60s — which is visually almost identical to what a
wrong secret produces. The two failure modes have to be told apart by reading
`lastError`, not by the symptom.

## Dashboard (M3-7)

`GET /` server-renders `run_summary`, `player_stats`, and `events` directly.
No CDN, no charting library — charts are hand-drawn inline SVG. Two of the
six charts named in docs/04 have a real M3 event source (tick p95, hit
latency); the other four render a named placeholder instead of fabricated
numbers — see docs/04 §Dashboard for why that's a deliberate divergence from
the original spec, not an oversight.

Verified against a real, regenerated dataset — not an empty schema:

```
$ npm --prefix sim run generate -- --runs 200 --days 14 --seed 42
done in 3.9s, 39 batch(es): accepted=89365 rejected=0 duplicates=0

$ npx tsx scratch-rollup.ts   (ad-hoc, deleted after use)
run_summary: 214 player_stats: 260
```

Loaded `http://127.0.0.1:8787/` in a real browser (not `curl`) and inspected
the live DOM:

```js
{"svgCount":2,"polylinePoints":"0.0,108.8 47.5,135.7 95.0,136.0 ...",
 "rectCount":9,"cardCount":8}
```

2 real `<svg>` charts, a `<polyline>` with real coordinates (not a placeholder
path), 9 histogram bars, and all 8 cards present — 2 stat cards, 2 live
charts, 4 named "not yet emitted" placeholders.

**A real bug, found only once a test exercised real aggregate data:**
`renderPage`'s number formatter called `.toFixed()` on the results of
`avg(value_extracted)`, `avg(duration_s)`, `avg(runs)`, `avg(extracts)`, and
`avg(deaths)`. Postgres `AVG()` over a numeric column returns `NUMERIC`,
which `pg` parses as a **string** rather than a `number` — precision it won't
silently truncate. The query's row types claimed `number | null`; that was
wrong, and `tsc` had no way to know it, since it doesn't model what `pg` does
with `NUMERIC` at runtime. An empty-table smoke test would never have
surfaced this — it only threw (`n.toFixed is not a function`, a 500) once
`GET /` ran against rows with a real average in them. `npm --prefix backend
test`: 59 passed, 7 new for this route.
