## A process error: three pre-existing stubs, overwritten without reading them first

`core/discovery/Rating.luau`, `Bucket.luau`, and `Recommend.luau` already
existed as M0-scaffolded stubs — `error("unimplemented: ...")` bodies with
a deliberately-designed API each, the exact situation M4's `Schema.luau`/
`Clamp.luau` were in and were correctly filled in against. This time the
stubs were overwritten with freshly-designed APIs without reading them
first, discovered only at `git add`, where they showed as `M` (modified)
rather than `A` (added) — a signal that should have been caught earlier.

Before deciding what to do about it: grepped the whole repo for the
original stubs' type and function names (`Bucket.of`, `Bucket.window`,
`Rating.decay`, `Rating.RunOutcome`, `Recommend.forPlayer`,
`Recommend.CooccurMatrix`, `SearchWindow`, `lastSeenTs`). Zero matches —
nothing downstream had been written against the original contracts yet, so
nothing broke. Kept the new APIs, documented each divergence in the
file's own header with the original signature quoted, rather than
reverting work that already passed real hand-computed tests. The actual
lesson, worth being plain about: check for existing `error("unimplemented:
...")` scaffolding before designing an API for a file that already has
one — recorded here so it isn't repeated in M6/M7.

## A three-way inconsistency, not the two-way one first assumed

docs/06 said new players start at `r = 1200, rd = 350`. So did the original
`Rating.luau` scaffold — both from the M0 scaffold, 2026-08-15. `backend/
src/rollup.ts` (M3-5, 2026-08-17, two days later) diverged to `1500`
without reconciling back to either. 1200 is not a standard Glicko value
anywhere in the literature; 1500 is. Resolved in favor of 1500 — the
domain-correct value for a system that calls itself "Glicko-style" — not
in favor of whichever artifact happened to be older. docs/06 and
`Rating.luau`'s own constant both updated to match the already-shipped,
tested rollup seed.

## M5-1: `core/discovery/Rating.luau`

docs/06 specifies the *shape* of the update (`r' = r + K(rd)*(actual -
expected)`, "shrink after each run, grow with absence") but not concrete
constants. Choices made and documented in the module itself:

- Expected performance: Elo-shaped logistic curve, 400-point scale, on
  `r - runDifficulty`.
- `K(rd) = 150 * (rd / 350)` — a brand-new player (`rd=350`) can swing up
  to ±150 in one run; an established player (`rd` near the 50 floor) moves
  only a few points even on a maximally surprising result.
- `rd` shrinks 6% per run (floor 50), grows 5 points per day absent
  (ceiling 350).

15 tests, hand-computed against clean fractions rather than re-derived from
the module's own formulas:

```
expectedPerformance(1900, 1500)  ->  10/11  (a +400 rating gap)
expectedPerformance(1100, 1500)  ->   1/11  (a -400 rating gap)
shrinkRd(350)                    ->    329  (350 * 0.94)
growRd(200, 10 days)             ->    250  (200 + 5*10)
```

```

```

## M5-9: `core/discovery/Recommend.luau`

The literal accept case, hand-computed against docs/06's own worked
example: `cooccur=2, count(a)=count(b)=2` gives naive cosine similarity of
exactly `1.0` (matching the doc's "gets a similarity of 1.0" claim
verbatim), shrunk by `λ=10` down to exactly `1/6 ≈ 0.1667`.

**Found while writing the test, not the implementation:** a first-draft
fixture for the "ranks stronger co-occurrence higher" test set
`cooccur(itemB, owned) = 10` while `count(itemB) = 5` — impossible, since a
pair can never co-occur more often than either item's own total count. The
bug would have produced a passing-but-meaningless assertion (Luau has no
way to know that invariant); caught by hand-tracing the expected ranking
before trusting the test, not by the test framework. Fixed to a
self-consistent fixture (`owned` used 30 times, `itemA` 20 times/15
alongside `owned`, `itemB` 10 times/8 alongside `owned`) and reverified the
ranking by hand: `itemA` scores ≈0.367, `itemB` ≈0.205.

16 tests total in `tests/recommend.spec.luau`.
