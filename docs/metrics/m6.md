Real command transcripts and measured numbers for M6 (Economy). Everything
here is a real run, not a projection — see CLAUDE.md's "never fabricate a
metric" rule.

## M6-1 — core/economy/Ledger.luau

```
lune run tests
```
`tests/ledger.spec.luau`: duplicate idemKey no-op, negative-balance rejection
(and that a rejected idemKey is *not* marked seen — a corrected retry can
still land), balance = sum of applied deltas across 10,000 random entries

## M6-4 — core/economy/Controller.luau

```
lune run tests
```
`tests/controller.spec.luau`, 8 cases, all green. Every hand-computed value
was independently reproduced first via a small Node.js reimplementation of
the exact docs/07 PI formula (not derived from the Luau code) before being
encoded as an assertion — same convention as `tests/rating.spec.luau` in M5.

**Real, measured divergence from docs/10-ROADMAP.md's M6 exit bullet
("Days to converge from a 30% seeded imbalance < 14"):**

```
node -e '<PI formula, KP=0.35 KI=0.05 IMAX=2.0 MMIN=0.80 MMAX=1.25 MAXD=0.03>'
day 9:  clampedDays crosses the 3-day alert threshold (30%-too-generous-faucet scenario)
day 23: last day the ratio (multiplier-drift-30% scenario) sits outside the +-0.05 target band
day 24: first day it's inside the band and stays
day 100/150: ratio == 0.850000 (converged and stable)
```

Two scenarios were measured, both starting "30% off" but interpreted two
different ways since docs/07 doesn't disambiguate:

1. **Multiplier drifted 30% high** against an otherwise-calibrated economy
   (`baseFaucetRate=1000` such that ratio=0.85 exactly at multiplier=1.0,
   seed multiplier at 1.30). Converges, but not until **day 24** — the
   3%/day rate cap alone requires ~10 days to close a 30-point multiplier
   gap before the PI math gets a chance to work, and the resulting integral
   windup causes an overshoot past the target that takes another ~10+ days
   to settle. This is the scenario `tests/controller.spec.luau` encodes.
2. **A faucet genuinely 30% too generous** (`baseFaucetRate=1300` against a
   sink calibrated for `1000`). This **never fully converges** — `MULT_MIN`
   (0.80) only permits a 20% reduction, so the multiplier hits and holds the
   floor at ratio≈0.817, permanently short of 0.85. `clampedDays` climbs
   past the 3-consecutive-day alert threshold by day 9 and keeps climbing.
   This is the guardrail working exactly as docs/07 describes ("sustained
   clamping means the model is wrong, not that the gain is too low") — not
   a bug, but proof the `<14 days` target can't be universally true: some
   30%-imbalance scenarios cannot converge to 0.85 through the payout
   multiplier alone, by construction of the clamp range.

docs/07-ECONOMY.md's metrics table has been updated in the same commit with
a note pointing back here, per CLAUDE.md ("the spec is not sacred — but
silent divergence is forbidden"). Not retuning `KP`/`KI`/`MAX_DAILY_DELTA`
to hit 14 days here — doing that without a real population to validate
against would be guessing, and no downstream M6 task is gated on this exact
number.

## M6-8 — core/economy/Market.luau

```
lune run tests
```
`tests/market.spec.luau`: price-time priority (best price first, then
earliest-at-equal-price), fill price is always the resting/maker order's
price, partial fills rest the correct remainder, fee = `price * quantity *
FEE_RATE` exactly, cold-start price-band bypass (no vwap entry yet), exact
±40% band boundary accept/reject, `cancel` returns the exact remaining
quantity and removes the order. All green.

**Fuzz test — the accept criterion's "100k orders conserve currency and
items exactly":** 100,000 random buy/sell/cancel operations across 4 items
and 500 traders, seeded RNG. Conservation is checked the way this project's
tests are supposed to be — independently of the module's own bookkeeping:
the test tracks, per order id, every unit of quantity that `Market.match`
ever reported filled via its `Fill` records (not by reading the book's own
`.filled` field back), and at the end verifies every order that was ever
accepted is accounted for as exactly one of: still resting (book's
`.filled` matches the independently-tracked total exactly), fully filled
(tracked total equals original quantity), or canceled with the exact
remaining quantity returned. No order's tracked fill total ever exceeds its
own original quantity. Every fill's `buyerPid ~= sellerPid`, unconditionally,
across all 100k orders. Runtime: ~40s (dominates `lune run tests`'s total
time, up from ~10s before M6-8 — see whole-tree section below).

**Real bug the fuzz test caught (not a hand-written test):** the first
`Market.validate` rejected a pid's new order whenever they held *any*
resting order on the opposite side of that item, whether or not the two
prices could ever actually cross. A resting buy at 150 and a new sell at
200 from the same pid got rejected as "self-trade" even though those orders
could never fill each other — not wash trading by any real definition.
Every hand-written self-trade test used crossing prices, so all of them
passed under the wrong rule too; only the fuzz test's own sanity assertion
(`acceptedCount > 50000`, added as a "did this actually exercise matching
at scale" check) caught it — at fuzz scale (100k orders, originally 30
traders) book depth grew large enough that ~50% of *all* order flow was
rejected as self-trade. Fixed by requiring the same crossing-price
condition `Market.match`'s own self-trade skip already used. Also bumped
the fuzz harness from 30 to 500 traders: even after the fix, 30 traders
placing thousands of orders each on both random sides of 4 items meant most
traders legitimately held crossing liquidity on both sides most of the
time, so self-trade rejections stayed a large (~46%), not-representative
fraction of traffic; 500 traders brings it down to a meaningful-but-minority
~18-24%, closer to what a real, larger population would look like.

Scope note (see the module's own header comment): `Market.luau` never
touches currency. `Fill.fee` is a computed number for M6-9's escrow layer
(backed by `core/economy/Ledger.luau`) to turn into real ledger entries.
`book.vwap7d` is caller-owned input — a backend rollup job's responsibility
to compute from trade telemetry (mirroring the M5 recommender-pairs
worker), not something `Market.luau` maintains itself.

## M6-2 — core/economy/WriteBehindQueue.luau

```
lune run tests
```
`tests/writeBehindQueue.spec.luau`, all green. No pre-existing stub existed
for this one (unlike Ledger/Controller/Market), so it was designed fresh —
generic over the stored value type, living alongside the other M6 pure-core
modules under `core/economy/`.

The one behavior worth calling out: due-ness is evaluated per-key
independently (nil-or-elapsed-since-`lastWriteTs`), which means the set of
"due" keys is not always a prefix of the FIFO dirty-order queue. A key
flushed at t=0 and re-dirtied at t=0.5 is still inside its 6s cooldown at
t=2, while a completely different key that first went dirty at t=1 (never
written before) is immediately due — even though it's queued *behind* the
first key. `drain` has to do a stable filter over the whole queue rather
than a cheap prefix cut; encoded as its own named test case rather than
just asserted for a single simple queue order.

## M2–M6 audit pass

A full read-through of everything built across M2–M6, looking for the kind
of defect a green test suite doesn't catch. Seven real bugs found and fixed;
each got a regression test that fails against the old code first. Two
recurring themes are worth naming, because both will keep producing bugs if
not watched for:

**1. Guards that check NaN but not infinity.** Three separate modules
rejected NaN and let `inf` through, and in each case `inf` produced exactly
the silent corruption the NaN check existed to prevent:
- `Quantize.encodeYaw` — `inf % TAU` is NaN in Lua, so an infinite yaw came
  back NaN and `buffer.writeu8` wrote it as `0` with no error at all.
- `FireValidation.sanitizeDirection` — an infinite component normalised to
  NaN (`inf/inf`); separately, three merely *large* finite components
  (`1e200` each) overflowed the magnitude to `inf` and collapsed the result
  to exactly `(0,0,0)`. Both are values the function documents that it never
  returns, and `CombatService` rejects a fire request purely on a `nil`
  return here, so both bypassed the `bad_direction` rejection entirely.
- Backend `validateEnvelope` — `ts`/`seq` bounded only as "finite"/"integer",
  then fed to `new Date(ts*1000).toISOString()` (throws past ~8.64e12) and a
  Postgres `bigint` column (errors past ~9.22e18). One bad line 500'd the
  whole POST and destroyed every valid sibling in the batch — the exact
  failure per-line validation exists to contain.

**2. Tests whose fixtures hid the bug they were meant to catch.** Three of
the seven survived because the test data made the wrong behaviour and the
right one indistinguishable:
- `Clamp.apply` fell back to the literal `"even"` for `spawnPattern` instead
  of the FSM baseline, but the clamp fixture's baseline *was* `"even"`.
  The FSM emits `flank` in PRESSURE and `chokepoint` in SPIKE, so a
  malformed model field silently downgraded a deliberate pacing decision —
  the model changing gameplay by failing. docs/05 specified the literal;
  code and doc were corrected together.
- `MovementGuard`'s out-of-bounds branch overwrote a standing teleport
  correction with `clamp(newPos)`, so breaking *two* rules produced a
  weaker correction than breaking one: a cheater was moved to the world
  boundary instead of back where they started, a repeatable long-distance
  teleport. The existing out-of-bounds test drove this exact path but
  asserted only on `reasons`, never `correctedPos`.
- `Market`'s fuzz test asserted item conservation but never currency
  conservation, despite the accept criterion saying "conserves currency and
  items exactly."

**3. `Ledger.apply` collapsed two incompatible outcomes onto one boolean.**
`false` meant both "duplicate, already counted" (which docs/07 says to treat
as success) and "rejected, insufficient funds" (which must not be). A caller
following the documented rule would hand over goods without taking currency
— the duplicate-grant bug the ledger exists to prevent, arriving through the
error path. docs/07's own signature could not express the rejection it
separately requires; both corrected.

**4. Float fees against a BIGINT currency.** `Market` computed
`fee = price * qty * 0.05` as a float while the ledger stores credits as
`BIGINT`. Rounding fee and proceeds independently fails to conserve currency
for 5% of integer amounts — `gross=10` gives `fee=0.5`/`proceeds=9.5`, which
round to 1 and 10 and **create a credit from nothing**. Prices are now
required to be integers, `fee = floor(gross * FEE_RATE)`, and proceeds are
`gross - fee` by subtraction. The fuzz test now asserts
`sellerReceived + fees == buyerPaid` exactly across all 100k orders.

Also added a drift guard tying `Snapshot`'s hardcoded byte budget to
`config/Netcode`: `tools/validate-config.luau` does all its packet-capacity
and bandwidth reasoning against the config copy while the encoder enforces
its own, and nothing checked the two agreed — with CLAUDE.md listing that
budget as a silently-breaking item.

## Playtest bug: jumping got players kicked

Reported from a live playtest — pressing space produced a stutter, a wall of
`Remote event invocation queue exhausted for ...PositionCorrection` warnings
doubling 1→2→4→8→16→…, and then
`[MovementGuard] kicking BirdMasterSC: speed score=21.6`.

One root cause with two visible symptoms. `MovementGuard.check` measured a
single **3D** displacement against `maxSpeed`, which is a **walk** speed
(16 studs/s). Gravity is not: a default Roblox jump leaves the ground at
`sqrt(2 * 196.2 * 7.2)` = 53.15 studs/s, and a fall keeps accelerating. So
the guard charged players for gravity.

Measured in a real Play session with the player standing **completely
still** — horizontal displacement `0.00` on every tick:

```
allowance/tick = 1.080 studs
t08 horiz=0.00 vert=1.97 score=1.8 ok      [speed]
t09 horiz=0.00 vert=1.76 score=3.4 ok      [speed]
t11 horiz=0.00 vert=1.16 score=4.4 ok      [speed]
t12 horiz=0.00 vert=1.37 score=5.6 correct [speed]
```

A standing jump costs 2.57x the allowance per airborne tick; a fall reaches
9.08x. `correct` fires 12 ticks in — that is the stutter, the server CFraming
the player back mid-air — and repeated jumps reach `kickAt = 20`.

The `PositionCorrection` spam was the same bug's second face: **nothing on
the client was connected to that remote at all**. A remote that is fired but
never consumed backs up its queue, and the log names the symptom rather than
the cause. It also meant corrections never reliably landed, since Roblox
network-owns the character and a server-side `CFrame` write is a request the
client's physics can overwrite — so the server kept seeing the same position
and kept scoring it.

**Fixes.** Horizontal and vertical are now budgeted separately: horizontal
against `maxSpeed` (unchanged, still the real anti-speed-hack check), rise
against the jump impulse the engine actually reports, fall generously
(`MAX_FALL_SPEED`, gravity is not a cheat). `CorrectionController` consumes
`PositionCorrection`, snapping position and zeroing velocity so the
correction sticks instead of being re-flagged next tick.

**A hole the first fix opened, found by probing rather than assuming.** With
only a per-tick vertical budget, a fly hack rising at 40 studs/s scored
`0.00` — it is *below* the ~66 rise budget, so every individual frame is
indistinguishable from a jump. Instantaneous speed cannot separate them;
duration can, because gravity ends a real jump in `v0/g` (~4 ticks above
walk speed). A `risingTicks` counter now flags a sustained climb, and it
only counts ticks rising faster than the player's own ground speed — so
walking up a ramp, however long, never accumulates.

Verified in Studio against the live guard, real physics:

```
--- cheats (must be caught) ---
fly slowly, 40 studs/s sustained     score= 49.55 kick  sustained_rise
fly fast, 400 studs/s                score= 44.14 kick  vertical_speed
speed hack 60 studs/s                score= 27.33 kick  speed
speedhack masked by falling          score= 27.33 kick  speed
--- legitimate (must NOT be caught) ---
full jump arc (real physics)         score=  0.00 ok
walk at full speed                   score=  0.00 ok
walk up a 60%-grade ramp             score=  0.00 ok
long fall                            score=  0.00 ok
sprint + fall                        score=  0.00 ok
stand still                          score=  0.00 ok
```

End to end in a live session: 8 real `PositionCorrection` fires produced
**zero** queue warnings, and 5 real jumps produced **0 violations, 0
corrections**, player still connected. Previously: kicked at 21.6.

`tools/validate-config.luau` gained a cross-check that a legal fall cannot
cover more ground per tick than `TELEPORT_THRESHOLD` allows — otherwise the
fall budget and the teleport check contradict each other and every long drop
reads as a teleport. Confirmed it rejects `MAX_FALL_SPEED = 900`
("a legal fall covers 60.8 studs/tick, past TELEPORT_THRESHOLD of 40").

**Why the audit pass missed this**, having touched this exact file: every
pre-existing MovementGuard test moved along a single horizontal axis. The
vertical axis was untested, so no fixture could distinguish a guard that
understood gravity from one that did not — the same "fixtures hide the bug"
pattern already flagged above, now with a fourth instance. The new tests
cover jump, fall, ramp, run+jump, and both fly-hack shapes.

Separately noted, not fixed: `MovementGuardService.setWorldBounds` is never
called anywhere, so `worldMin`/`worldMax` are always nil and the
out-of-bounds branch is dead code in practice. The audit-pass fix to its
correction precedence remains correct for when it is wired up.

## M6-3 / M6-5 / M6-6 / M6-7 / M6-9 / M6-10

### M6-9 — Escrow (`core/economy/Escrow.luau`)

```
lune run tests   -- tests/escrow.spec.luau
```
Both accept criteria are direct tests. `EscrowState` owns inventories **and**
escrowed holdings in one structure, rather than escrow being a separate thing
kept in sync with an inventory elsewhere: two structures that must agree
eventually disagree, one cannot.

The end-to-end fuzz drives Escrow and Market together for **20,000 random
place/cancel/match operations** and asserts credits and items are conserved
exactly, with non-negativity checked continuously rather than only at the end.
Sanity assertions (`placed > 1000`, `settled > 100`, `cancelled > 100`) keep
the run from passing vacuously.

Correctness point worth naming: a fill **refunds the buyer's price
improvement**. They escrow at their own limit but pay the resting maker's
price, and a book that quietly keeps the difference is stealing. Refunding per
fill rather than at cancel is also what keeps `creditsHeld` equal to true
remaining exposure — which is what makes the exact-escrow cancel path exact.

### M6-3 — Payouts, verified in Studio

`economyRunProbe` drives a full run through the real `EconomyService`:

```
insurance_premium (sink)        -360  NEGATIVE  OK
extract faucets                +2400  POSITIVE  OK
repair+ammo (sinks)             -575  NEGATIVE  OK
insurance_claim (faucet)        +800  POSITIVE  OK
M6-3 accept: every reason code signed correctly -> PASS
```

The sign is derived once from `Ledger.FAUCETS`/`SINKS` rather than trusted to
call sites, so a sink cannot ship a positive delta and silently become an
unplanned faucet. `repairCost`/`ammoCost` take **no multiplier argument at
all** — docs/07 says the controller tunes faucets only, and the type makes
that unbreakable instead of a rule everyone has to remember.

**A first result that looked like a bug and was not.** The initial probe
reported a *zero*-signed premium. Cause: it bought insurance at a zero
balance, and the ledger correctly rejected it for `insufficient_funds`. The
probe was unrealistic, not the sign rule — a real player arrives with credits
from previous runs. The probe now seeds a balance, and the negative-balance
guard is confirmed working in-engine as a side effect.

Insurance claims are capped at the declared value the premium covered.
Uncapped, insuring a trivial carry and dying on a fortune pays 40,000 against
an 18-credit premium, turning the economy's most interesting sink into its
largest faucet.

### M6-7 — Reconciliation

```
backend: "2,000 simulated runs reconcile with zero mismatches"  (~7.8s)
```
The accept criterion, run for real: 2,000 runs across 40 players through real
ledger rows in real Postgres, reconciled. Zero mismatches.

Two independent checks, and the second is the one that earns its keep:
ledger-sum vs the game's cached balance catches drift *between* stores, but if
the authoritative store is itself corrupt then a cache agreeing with it is
also wrong and that comparison passes. So the `balance_after` chain inside the
ledger is verified separately — proven by a test that corrupts a
`balance_after` and sets the cache to match it, where only the chain check
fires.

The job **never mutates**. docs/07 is explicit that a nonzero count is a bug
report and not a tuning knob; a job that silently rewrites balances destroys
the evidence needed to find out why they diverged, and would happily launder a
duping exploit into a legitimate-looking number. A test asserts both stores
are byte-identical after a reconcile that found a mismatch.

A player with ledger entries but no cache row is deliberately **not** a
mismatch: M6-2's write-behind queue coalesces at one write per player per 6s,
so a player whose first payout landed seconds ago legitimately has no cached
row yet, and counting that as drift would make zero mismatches unreachable by
construction.

### Test isolation: `fileParallelism: false`

Every backend suite runs against one real local Postgres on purpose. The
consequence is that parallel test *files* are not independent, and both
failure modes showed up for real here:

- `economy.test.ts` counted rows from `run_summary` that another file had
  inserted, pushing a "sample too small" case over the threshold so it passed
  for the wrong reason.
- `reconcile.test.ts`'s 2,000-run fuzz saturated Postgres hard enough that
  ingest's 10,000-line performance assertion measured **590ms against its
  500ms budget** — while measuring **396-419ms run alone**, three times in a
  row.

The second is why the fix is a config change rather than tidier fixtures.
docs/04's criterion is a claim about the *server*; measuring it while another
suite hammers the same database measures something else and calls it that
claim. A performance assertion whose result depends on what else happens to be
running is worse than no assertion, because it teaches you to ignore red.
Suite goes from ~10s to ~17s and is now deterministic across repeated runs.
