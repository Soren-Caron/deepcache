# M4 Metrics

Measured numbers, captured as they were produced. Every claim here is
reproducible by running the command shown.

## Provider pivot: Anthropic API → Ollama (self-hosted)

Decided at M4 kickoff, before any M4 code was written. See `CLAUDE.md` §Model
choices and docs/05 §Model selection and cost for the full rationale; this
section is the real numbers behind that decision.

Installed Ollama 0.32.14, pulled two models onto local hardware (RTX 5070
laptop GPU, 8GB VRAM, misreported by Windows as 4GB — a known WMI quirk, not
an actual limitation):

```
ollama pull llama3.2:3b   -> 2.0 GB  (director ticks)
ollama pull llama3.1:8b   -> 4.9 GB  (pre-run briefing, post-run debrief)
```

**Real measured latency**, a tick-shaped request through the actual
structured-JSON-output path (`/api/chat`, `format` = the director decision's
JSON schema), against the 1200ms tick budget from docs/05:

```
cold (model not yet loaded): total_duration ≈ 40.6s (load_duration ≈ 21.7s)
warm request 1:                total_time  ≈ 0.905s
warm request 2:                total_time  ≈ 1.009s
```

Under budget when warm, but by a real margin of roughly 15-25%, not
comfortable headroom — a measurable `fallbackUsed` rate should be expected
once M4-6 lands, not treated as a bug if it shows up. Cold start is the
sharper risk: Ollama's default idle-unload (~5 min) would reintroduce that
40s load cost mid-run if the tick model were ever allowed to go idle between
20s ticks. Mitigated with `keep_alive` pinned on every request rather than
left at the default — a decision made from this measurement, not before it.

Output quality on the first real request, unprompted beyond the system
message: valid, schema-conformant JSON (`tighten_squeeze` / `chokepoint` /
`hold_terminal`, coherent bark text) — a reasonable starting signal for
prompt design work in M4-2, though not a substitute for it.

## M4-3/M4-4: `/v1/director/tick` + fallback JSON extraction

```
npm --prefix backend test  -- 9 new (director.test.ts) + 11 new (fallback.test.ts), all pass
```

Real bug caught by the array test case: `typeof [] === "object"` in
JavaScript, so `parsed === null || typeof parsed !== "object"` alone let a
syntactically-valid-but-wrong-shaped JSON array through as if it were a
proposal object. Fixed with an explicit `Array.isArray` check.

**`MAX_OUTPUT_TOKENS`, tuned from a real measurement, not a guess.** First
draft mirrored the old Anthropic plan's `max_tokens: 400`. A real call
against the actual full ~2300-token system prompt (not the short synthetic
probe used for the initial Ollama feasibility check) showed:

```
prompt_eval_count: 2302   prompt_eval_duration: 110ms
eval_count:          93   eval_duration:        795ms   (~8.5ms/token)
total_duration:                                1100ms
```

Output generation, not prompt processing, is the dominant cost — the
~2300-token prompt only cost 110ms to process. A 400-token cap would allow a
~3.4s worst case if the model ever rambled past the schema; tightened to
150, well above the 93 actually observed, but a real hard ceiling on a
runaway generation instead of one 13x looser than needed.

**Real end-to-end timeout-rate measurement, against the actual running
route (real Ollama, real full prompt, no mocks) — 10 consecutive calls:**

```
5/10 succeeded (950-1010ms), 5/10 timed out (1200-1215ms)
```

Bimodal, not evenly-distributed jitter — the successful and failed calls
each clustered tightly, suggesting GPU/thermal ramp-up or contention with
everything else running on the same dev machine, not random noise. **50%
is a real, measured number, materially worse than the ~0% the earlier
short-prompt latency probe suggested** — that earlier number used a ~250-word
placeholder system prompt, not the real ~1435-word one this route actually
sends. Flagged to the user as a real decision point (the 1200ms budget is
inherited from the original cloud-API plan and nothing technically requires
keeping it now that the provider changed); the user chose to defer that
specific tuning decision and continue the rest of M4, so the timeout stays
at 1200ms for now, with this number on record rather than hidden.

## M4-5: `Clamp.luau`

33 cases in `tests/clamp.spec.luau`: 23 explicit malformed-input cases (nil,
`{}`, wrong types on every field, NaN/±inf `spawnMultiplier`, out-of-range
and negative values, unknown enum values, unknown objective param keys,
out-of-range objective params, fractional `threatTier`, non-string/oversized/
control-character `bark`, every field malformed simultaneously, deeply
nested garbage), plus dedicated `rateLimited`/`sanitizeBark` unit tests.
Every case asserts full decision validity (in-enum, in-range, correct
types), not just "didn't throw."

```
lune run tests   -- 505 passed, 20 todo (up from 457 passed, 22 todo)
```

**Two bugs caught in my own first-draft tests, not in `Clamp` itself:**
`rateLimited` always applies its delta-from-`previous` window alongside the
absolute-range clamp, so a test asserting "clamps to the absolute range"
with a `previous` too close to that range's edge was asserting a value the
function could never actually return — the delta window was binding first.
Fixed by widening `maxDelta` in that specific case to isolate the behavior
under test, rather than changing `Clamp` to match a wrong expectation.

**Scope note:** docs/05's clamping table lists "`objective.id` must be in
the whitelist and not currently on cooldown" as a single rule. Cooldown
tracking is stateful; `Clamp` is pure and has no notion of time, so it can
only own the whitelist half. Cooldown enforcement is M4-8's job (the
objective system) — documented explicitly in docs/05 rather than left as a
silent gap, with two tests asserting the split.

## M4-6: `DirectorService`

First time `core/director/Fsm` (M2-9) has been wired into a live game —
until this task it existed only as tested pure core. Verified for real in
Studio Play mode via the `DeepcacheDiagnostics` bridge (`directorInfo`,
`directorForceTick`), not simulated:

```
Baseline tick stats before any director call:
  p50=0.098ms p95=0.143ms overruns=0  (288 ticks)

After 2 real director calls (one succeeded, one timed out at 1233ms):
  p50=0.104ms p95=0.130ms overruns=0  (739 ticks)
```

Tick timing is unaffected by the async director call, exactly as designed —
the HTTP request runs on its own thread and the 20Hz Heartbeat loop never
awaits it.

**The real failure drill — backend process killed for real, not simulated:**

```
[backend killed via Stop-Process; /healthz confirmed unreachable]

4 forced director ticks:
  tick 1: fsmState=PRESSURE  lastError=timeout  calls=4
  tick 2: fsmState=SPIKE     lastError=timeout  calls=5  skipped=1
  tick 3: fsmState=SPIKE     lastError=timeout  calls=6  breakerOpenFor=59.9s
  tick 4: fsmState=LULL      lastError=timeout  calls=6  breakerOpenFor=59.9s (unchanged -- no new call fired)
```

FSM advanced through real state transitions (`PRESSURE → SPIKE → SPIKE →
LULL`) with a valid decision every tick throughout the outage. Breaker
opened after 3 consecutive real failures and correctly stopped firing new
calls while open (`calls` plateaued at 6 across ticks 3 and 4).

```
[backend restarted; real 65s wait for the breaker window to elapse]

tick N:   lastError="" (cleared -- a real call succeeded), calls=10
tick N+1: fallbacks unchanged (the pending proposal from tick N was applied)

Final tick stats across the whole drill: p95=0.206ms, 0 overruns, 4626 ticks
```

Full recovery — not assumed from the breaker merely closing, confirmed by
watching a real proposal actually get applied on the tick after the
successful call landed, per the documented one-tick-lag "apply at the next
boundary" design.

**A real, honest gap, not fabricated data:** the run-state payload sent to
the backend has real values for `aliveEnemies` (`EntityService.count()`) and
`secondsSinceLastFight` (derived by watching `CombatService.getMetrics().
hits` for real increases), but `0`/`"unknown"` placeholders for per-player
kills/deaths, zone, and the rest of `pressure` — none of that is tracked
live anywhere in the codebase yet. `core/sim/Budget` (M2-8) was never wired
into `EntityService` either, a pre-existing M2 adapter gap this surfaced
rather than caused.

**A prompt-quality finding, not a bug:** across multiple real, differently-
timed calls, the model reproduced one worked example's exact bark text
("One less mouth to feed...") verbatim rather than generating original text
for the specific situation each time. Left as-is for this task (about the
adapter's mechanics, not prompt quality) but worth a v2 prompt iteration.

## M4-7: Bark filtering

`config/CannedBarks.luau` pool reduced from docs/05's original "~40 per
intent" to 8 — reasoning kept in the file itself, not just here: a run is at
most 36 director ticks total across all eight intents combined, and a
filter failure is the exceptional path, not the common one.

**Verified in Studio by forcing a real failure, not a mocked one** — userId
`0` genuinely fails `FilterStringAsync`:

```
in:  "SECRET RAW TEXT: shot 10, kill" (intent=punish_greed, userId=0)
out: "You wanted the good stuff. Here's the cost."   <- confirmed present
     in the real punish_greed pool, not just plausible-looking
```

Happy path confirmed separately with a real connected player's UserId: real
text passed through unchanged, so the failure case above isn't a permanently
over-cautious fallback — it only engages when filtering genuinely fails.

```
tick stats before/after wiring async filtering into the tick flow:
  0 overruns, p95 0.10-0.15ms across 1,058 ticks
```

## M4-8: Objective cooldown gate

`core/director/Objectives.luau` completes the split `Clamp.luau` (M4-5)
documented: Clamp owns "in the whitelist" (stateless), this owns "and
available right now" (stateful cooldown).

```
lune run tests   -- 515 passed, 20 todo (up from 505)
```

**Verified in Studio against the real, synced module** (not just Lune),
driving a scripted accept/reject/re-accept sequence directly:

```
propose purge_node at t=10 (never issued)         -> accepted
propose hold_terminal at t=50 (on cooldown to 160) -> rejected, stays purge_node
propose hold_terminal at t=160 (cooldown elapsed)  -> accepted
```

Wired into `DirectorService`: a rejected candidate keeps the previously-
active objective's id *and* params, not fresh defaults — an objective in
progress does not restart because a competing one was proposed and blocked.
Tick stats unaffected: 0 overruns, p95 0.14ms across 760 ticks.

**Scoped honestly:** `objective.issued` telemetry is real, firing on every
genuine change. `objective.complete` is not implemented — it needs
per-objective-type gameplay hooks (zone-standing timers, node-destroy
tracking, cart-delivery tracking) that don't exist anywhere in the codebase
yet, the same category of gap M4-6 already documented for kills/deaths.

## M4-10: A/B arm assignment

`core/director/AbTest.luau` reuses the already-tested `Hmac.sha256` instead
of a second hash implementation. The accept criterion, run for real:

```
1,000 simulated runIds -> A=484 B=516 (48.4%), inside the 48-52% window
lune run tests   -- 519 passed, 20 todo (up from 515)
```

**Verified end to end, not just at the pure-function level** — a live
Studio run's actual arm was recomputed independently from its `runId` and
matched the arm actually driving call behavior (arm B, backend calls were
incrementing), and the real database confirms it landed in `run.start`:

```sql
SELECT payload->>'arm' FROM events WHERE type='run.start' AND run_id='1-2d93a238-...';
 arm
-----
 B
```

Arm A is wired as a true control condition, not a disabled feature:
`DirectorService` never calls the backend at all when the run's arm is A,
because `Clamp.apply(nil, fsmDecision, bounds)` already made that tick's
decision the pure FSM baseline before the arm check even runs.
