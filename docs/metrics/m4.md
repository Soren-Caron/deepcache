# M4 Metrics

Measured numbers, captured as they were produced. Every claim here is
reproducible by running the command shown.

## Provider pivot: Anthropic API → Ollama (self-hosted)

Decided at M4 kickoff, before any M4 code was written. See `CLAUDE.md` §Model
choices and docs/05 §Model selection and cost for the full rationale; this
section is the real numbers behind that decision.

Installed Ollama 0.32.14, pulled two models onto local hardware (RTX 5070
laptop GPU, 8GB VRAM, misreported by Windows as 4GB — a known WMI quirk, not
an actual limitation):

```
ollama pull llama3.2:3b   -> 2.0 GB  (director ticks)
ollama pull llama3.1:8b   -> 4.9 GB  (pre-run briefing, post-run debrief)
```

**Real measured latency**, a tick-shaped request through the actual
structured-JSON-output path (`/api/chat`, `format` = the director decision's
JSON schema), against the 1200ms tick budget from docs/05:

```
cold (model not yet loaded): total_duration ≈ 40.6s (load_duration ≈ 21.7s)
warm request 1:                total_time  ≈ 0.905s
warm request 2:                total_time  ≈ 1.009s
```

Under budget when warm, but by a real margin of roughly 15-25%, not
comfortable headroom — a measurable `fallbackUsed` rate should be expected
once M4-6 lands, not treated as a bug if it shows up. Cold start is the
sharper risk: Ollama's default idle-unload (~5 min) would reintroduce that
40s load cost mid-run if the tick model were ever allowed to go idle between
20s ticks. Mitigated with `keep_alive` pinned on every request rather than
left at the default — a decision made from this measurement, not before it.

Output quality on the first real request, unprompted beyond the system
message: valid, schema-conformant JSON (`tighten_squeeze` / `chokepoint` /
`hold_terminal`, coherent bark text) — a reasonable starting signal for
prompt design work in M4-2, though not a substitute for it.

## M4-5: `Clamp.luau`

33 cases in `tests/clamp.spec.luau`: 23 explicit malformed-input cases (nil,
`{}`, wrong types on every field, NaN/±inf `spawnMultiplier`, out-of-range
and negative values, unknown enum values, unknown objective param keys,
out-of-range objective params, fractional `threatTier`, non-string/oversized/
control-character `bark`, every field malformed simultaneously, deeply
nested garbage), plus dedicated `rateLimited`/`sanitizeBark` unit tests.
Every case asserts full decision validity (in-enum, in-range, correct
types), not just "didn't throw."

```
lune run tests   -- 505 passed, 20 todo (up from 457 passed, 22 todo)
```

**Two bugs caught in my own first-draft tests, not in `Clamp` itself:**
`rateLimited` always applies its delta-from-`previous` window alongside the
absolute-range clamp, so a test asserting "clamps to the absolute range"
with a `previous` too close to that range's edge was asserting a value the
function could never actually return — the delta window was binding first.
Fixed by widening `maxDelta` in that specific case to isolate the behavior
under test, rather than changing `Clamp` to match a wrong expectation.

**Scope note:** docs/05's clamping table lists "`objective.id` must be in
the whitelist and not currently on cooldown" as a single rule. Cooldown
tracking is stateful; `Clamp` is pure and has no notion of time, so it can
only own the whitelist half. Cooldown enforcement is M4-8's job (the
objective system) — documented explicitly in docs/05 rather than left as a
silent gap, with two tests asserting the split.
