# M1 Metrics

Measured numbers, captured as they were produced. Every claim here is
reproducible by running the command shown.

## Snapshot serialization

`lune run tools/loadtest/serialize` — 10,000 iterations per measurement,
Windows 11, Node-free pure Luau under Lune 0.10.5.

| Set | Keyframe encode | Keyframe decode | Delta encode | Delta apply | Keyframe bytes | Delta bytes |
|---|---|---|---|---|---|---|
| 8 entities, 50% moving | 2.5 µs | 2.8 µs | 5.2 µs | 2.6 µs | 93 | 49 |
| 32 entities (interest cap), 25% moving | 9.6 µs | 10.7 µs | 20.9 µs | 5.7 µs | 357 | 82 |
| 81 entities (packet max), 25% moving | 23.1 µs | 24.1 µs | 48.0 µs | 11.5 µs | **896** | 192 |

**Bytes per entity: 11.06** at the packet maximum — the 11-byte record plus an
amortized 5-byte header, exactly as designed.

**896 bytes at 81 entities**, under the 900-byte budget and comfortably under
the ~1000-byte `UnreliableRemoteEvent` drop threshold. This is the number the
whole wire format exists to hit.

### Projected bandwidth

**1.87 KB/s per client** at the 32-entity interest cap, against a 6 KB/s
budget — 31% of allowance.

Derived as one keyframe per second plus 19 deltas (`357 + 82 × 19 = 1915 B/s`).
Asserted in the benchmark, so a format change that blows the budget fails CI
rather than surfacing in a playtest.

### Known optimization, deliberately deferred

Delta encode costs roughly **2× keyframe encode** (48 µs vs 23 µs at 81
entities) because `encodeDelta` rebuilds the baseline record map on every call.
Caching that map per client would remove most of it.

Not worth doing yet: at 4 players × 20 Hz the total is ~3.8 ms per *second* of
wall clock, against a 50 ms tick budget. Revisit only if `TickBench` shows
replication as a real share of the tick.

## Roblox VM parity

Verified through the Studio MCP bridge on the `Edit` datamodel — **32 checks,
all pass**. The pure core is plain Luau on top of these primitives, so if they
match, the modules do.

| Group | Checked |
|---|---|
| `buffer` | `readu16`/`readi16`/`readu8`/`readu32` at their exact width boundaries (65535, ±32768/32767, 255, 4294967295) |
| `bit32` | keyframe-flag packing into the count byte's high bit and its extraction |
| Modulo sign | `-0.5 % TAU > 0`, `-1 % 256 == 255` — yaw wrapping depends on Lua's `%` taking the divisor's sign, not C truncation |
| `math.round` | half-away-from-zero at 0.5, −0.5, 2.5 |
| Quantize values | the exact cases pinned by the Lune suite, including int16 saturation and `encodeYaw(TAU − 1e⁻⁹) → 0` |
| Snapshot geometry | capacity 81, `byteSize(81) == 896`, under the 1000-byte drop threshold |
| `table` / interpolation | `create`, `clone`, `find`, backtick strings |
| Engine classes | `UnreliableRemoteEvent` instantiates |

One cosmetic difference: `encodePosition(-0.024)` yields `-0` in Roblox rather
than `0`. Numerically equal (`-0 == 0` is true), and `buffer.writei16` stores it
as 0, so delta comparison and the wire format are unaffected.

## In-engine measurements

Run in a live Studio play session through the MCP bridge, via
`ServerStorage.DeepcacheDiagnostics`.

### Server tick budget

`bridge:Invoke("bench", { entities = 40, ticks = 200 })` — 40 entities is the
documented design point.

| | ms |
|---|---|
| p50 | 0.87 |
| p95 | **1.16** |
| p99 | 1.40 |
| worst | 3.82 |
| **budget** | **12.00** |
| overruns | 0 |

**9.7% of budget at p95.** Per-phase mean: `sim` 0.739, `replication` 0.122,
`history` 0.040, `movement` 0.005, `combat` 0.001 ms.

### Where the budget actually breaks

`benchSweep` — more useful than a pass mark, because it says how much room M2's
content has.

| Entities | p50 | p95 | p99 | sim | repl | Verdict |
|---|---|---|---|---|---|---|
| 40 | 0.84 | 1.18 | 1.30 | 0.71 | 0.12 | OK |
| 80 | 2.11 | 2.79 | 3.08 | 1.99 | 0.14 | OK |
| 120 | 3.89 | 4.71 | 4.79 | 3.74 | 0.18 | OK |
| 200 | 10.07 | 12.73 | 14.22 | 9.89 | 0.29 | **over** (7 overruns) |
| 300 | 22.75 | 25.70 | 26.89 | 22.30 | 0.40 | **over** (100 overruns) |

**Breaks between 120 and 200 entities — 4× headroom at the design point.**

`sim` dominates and scales super-linearly (7.5× the entities → 31× the time),
which is the O(n²) neighbour loop in `EntityService.step` behaving exactly as
its comment predicted ("revisit past ~150 entities"). Replication scales
linearly and stays negligible. A spatial hash is the fix when M2 needs it.

### Bandwidth

Live session, 40 Skitters all actively chasing one player:

| | KB/s |
|---|---|
| Typical (~25% moving, computed) | 1.87 |
| Worst case (all 32 visible moving, computed) | 6.97 |
| **Measured, live, all chasing** | **6.10** |
| Budget | 8.00 |

**The original 6 KB/s budget was unsatisfiable** alongside a 32-entity interest
cap: `(5 + 32×11) × 20 = 6.97 KB/s`, and only 27 entities fit 6 KB/s. Raised to
8 KB/s — seeing the crowd matters more in a shooter than 1 KB/s, and 6 was an
invented target, not a platform limit. `validate-config` now cross-checks the
two, and the benchmark reads both constants from config instead of redeclaring
them (the local copies are how they drifted apart).

### Combat pipeline, end to end

Client fires at the **rendered** position — interpolated, ~100 ms behind server
truth — which is exactly the case lag compensation exists for.

| | |
|---|---|
| Static target, 5 shots | **5 hits, 0 misses (100%)** |
| Damage per body shot | 22 (matches Sidearm config) |
| Headshot | 39.6 = 22 × 1.8 multiplier |
| Killing blow | `damage: 20` against 20 HP remaining — **overkill clipped**, so a kill cannot over-credit |
| Round-trip p50 / p95 | 99.0 / 99.8 ms (Studio local; includes ~5 ms poll granularity) |
| Rejections | 0 rate, 0 ammo, 0 origin substitutions, 0 rewind clamps |

An earlier run read 60% and looked like a netcode fault. It was not: Sentry has
130 HP and the Sidearm does 22, so the sixth hit killed it and every later shot
correctly found a corpse. Every test had hit exactly as many times as it took to
kill. **The arithmetic, not the netcode, was the story** — but chasing it
surfaced a real bug (below).

### Corpse lifetime — bug found by running it

`candidates=0` in the resolver trace exposed that corpses were reaped **one tick
after death** instead of lingering `CORPSE_TICKS = 20`. The reap clock compared
against `spawnedAtTick`, which is almost always far in the past. Consequences:
the client never saw the `death` state (no ragdoll, no death animation), and a
shot fired just before the kill had nothing left to rewind onto.

Fixed with a dedicated `diedAtTick`, moved into `core/sim/EntityState`
(`markDeath` / `shouldReap`) so it is unit tested, per CLAUDE.md's rule that a
bug which cannot be expressed as a pure-core test is a layering problem.

Verified in-engine after the fix:

```
tickDelta=0..19   count=1  state=death     <- corpse persists
tickDelta=22+     count=0  state=reaped    <- reaped on schedule
```
