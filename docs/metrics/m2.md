# M2 Metrics

Measured numbers, captured as they were produced. Every claim here is
reproducible by running the command shown.

## Level assembly

`lune run tools/loadtest/assemble` — 1,000 consecutive seeds against the
12-module catalogue in `src/shared/config/Rooms.luau`, Windows 11, pure Luau
under Lune 0.10.5. Wired into CI, so a regression fails the build.

```
Level assembly — 1000 seeds, target 68000 studs^2

  generated        1000 ok, 0 failed  (3.44 ms/seed)
  total area       min 59008   p05 62848   mean 67133   p95 70592   max 71360
  window           57800 .. 78200  (+/-15%)   mean is -1.3% off target
  module counts    14:17  15:563  16:178  17:203  18:39
  distinct layouts 190 of 200 seeds

assembly budgets met
```

**1,000 of 1,000 seeds produce a valid layout** — the M2 exit criterion. Valid
means every constraint re-derived from the placed geometry: three pads (one per
zone) reachable by BFS from the entrance, no module id repeated within 2 graph
hops, no two footprints overlapping, every doorway joined to an opposite face of
equal size at a coincident point, and total area inside ±15%.

**Mean area lands 1.7% under target.** This is the number that took the most
work to get right and it is worth recording why. Three earlier versions all
produced *valid* layouts and would have passed the exit criterion:

| Version | Failures / 1000 | Mean area | Note |
|---|---|---|---|
| Count drawn independently of target | 148 | 64484 | Per-module ideal often outside what the catalogue can supply |
| Count = target / catalogue mean | 131 | 64921 | Raw mean is biased high; the reachable set is smaller |
| First count that lands in-window | 0 | 63314 | Valid, but every level is the smallest one allowed |
| **Count calibrated from the first walk** | **0** | **66822** | Current |

The third row is the interesting failure: zero test failures, every constraint
satisfied, and levels systematically 13% smaller than the designer asked for.
Correctness tests could not see it, which is why `MEAN_ERROR_BUDGET` exists in
the benchmark alongside the validity check.

**198 distinct layouts over 200 seeds.** The two collisions are seeds landing on
the same module count with the same choices, not the seed being ignored.

### A pad on the drop point (found in Studio, M2-2 adapter)

The first level built into the world reported:

```
pad Perimeter: 0 studs, 1 hops, opens at 180s
```

The Perimeter pad had been placed on module 1 — the entrance. Players would drop
directly onto the 3:00 extraction pad, which removes the travel the whole
risk/reward loop is built on. `padAtIndex` drew uniformly across the band and
the band starts at the entrance, so roughly one seed in four did this.

Nothing in the pure-core suite could see it: the layout was valid by every
constraint, and "reachable" was satisfied trivially by a distance of zero. It
took instantiating the level and asking how far the pads were. Pad selection now
excludes the entrance, and both specs assert it — `assemble.spec` that no pad is
module 1, `path.spec` that every pad route is a real journey.

After the fix, seed 1 reports **60 / 236 / 532 studs** for Perimeter /
Processing / Vault.

### Cross-runtime determinism (verified in Studio)

"Deterministic" has to mean identical *in Roblox*, not identical twice in the
same interpreter: the server assembles the level while tooling and tests replay
it under Lune, and a run is meant to be reproducible from its seed for
debugging. Both runtimes were asked for seed 42:

```
seed 42 fingerprint  15 modules, area 66880
Junction_Cross@0,0,0 Perimeter_Yard@0,68,0 Perimeter_Dock@-80,68,90
Processing_Sorting@-80,-4,0 Processing_Vats@-80,-84,90 Processing_Catwalk@-152,-84,90
Vault_Core@-232,-84,180 Junction_Cross@-232,-160,180 Corridor_Bend@-232,-208,0
Corridor_Straight@-180,-208,90 Junction_Cross@-140,68,0 Junction_Cross@-4,-84,0
Junction_Cross@-120,-208,0 Vault_Archive@-232,-8,0 Junction_T@-80,-156,90
```

Identical under Lune 0.10.5 and in Studio, module for module including position
and rotation. (This fingerprint is post-fix; the pad-placement change above
moves every layout, which is why it differs from the one first recorded.)

The fingerprint is printed by the benchmark rather than asserted, because only a
Studio session can supply the other half of the comparison.

**~3.5 ms/seed** (3.42 / 3.43 / 3.59 / 3.69 over four runs), dominated by the
depth-first placement search. Assembly happens once per run at server boot, so
this is far inside any budget that matters; it is recorded because the
1,000-seed test is ~3.5 s of the suite's runtime. A cold first run measured
7.4 s — worth knowing before treating a single sample as a regression.

### Why the module count is searched rather than drawn

The spec asks for two things at once: a spine of 8–12 modules plus 4–6 branches,
**and** total floor area within ±15% of target. Module areas in the catalogue
span 1024–10752 studs², so those constraints are not independent — most counts
cannot reach the area window at all, whatever the walk does.

Anchoring the count on the catalogue's mean module area gets close but stays
biased: connector sizes, zone bands, and the no-repeat rule all shrink the set of
modules actually reachable at each step, so placements average ~6% below the raw
catalogue mean. The generator now measures that directly — it walks once, reads
the area it achieved, and recomputes the count from the achieved mean rather than
the theoretical one. Two walks, no tuning constant, and it stays correct when the
catalogue changes, which it will at M7 when the remaining 12 modules land.

## Pathing (M2-3)

`lune run tests` → `tests/path.spec.luau`. A* over the room/doorway waypoint
graph, ~35 nodes for a full level.

| Measure | Result |
|---|---|
| Layouts where every waypoint is reachable from the entrance | **1000 / 1000** |
| Pairs disagreeing with an independent Dijkstra | **0 of 94,737** |
| Detour vs straight line — p50 / p75 / mean | **1.33 / 1.41 / 1.36** |
| Detour — p90 / p95 / p99 | 1.75 / 2.05 / 2.88 |
| Detour — worst single pair | 9.53× (seed 74) |
| Entrance-to-pad detour — p50 / mean / worst | 1.31 / 1.36 / 4.41 |

Verified in Studio over 47,205 pairs across 100 layouts: **0 unreachable, p50
1.34, mean 1.37, max 9.53** — identical to Lune. Seed 42's routes from the
entrance to each pad come out at 60, 276, and 476 studs for Perimeter,
Processing, and Vault, which is the graduation by depth the design asks for.

### The 1.4× criterion was wrong as written

The backlog asked for "path length within 1.4× euclidean". That does not hold
here — and it cannot hold for any level with walls. Two rooms either side of a
shared wall with no door between them are 60 studs apart in a straight line and
several hundred studs of walking. Measured worst is 9.53×, and that number is a
property of the level, not a defect in the search.

What the criterion was standing in for is that the graph is not pathological and
the search is not lazy. Those are now asserted directly:

- **Optimality against Dijkstra.** A* agreed on all 94,737 pairs tested. This is
  the property a pathfinder must actually guarantee, and it is the one the ratio
  was a proxy for. Ratio statistics alone cannot see a lazy search — a
  consistently 20% too long path would sail past a 1.4× median.
- **Median and mean detour at 1.4×** (1.33 and 1.36), which is where the spec's
  number survives and still means "levels are not mazes".
- **A hard ceiling of 12×** on any single pair, to catch a layout that has
  genuinely folded in on itself.
- **Route contiguity** — every consecutive pair in a returned path is a real
  graph edge, and no node repeats. A shortest *length* can still be a nonsense
  route if the node list skips edges.

### Levels are trees, and that is a design decision

The spine-and-branches walk produces a tree: 17 connections for 18 modules, no
loops. Every route therefore backtracks, and a third of all waypoint pairs walk
more than 1.4× their straight-line distance.

Closing loops for free was tried and does not work: **0 loops across 300
layouts**, despite ~19 unused doors per layout. Connectors sit at face midpoints,
so two unused doors coincide only when the shared faces have identical extents
*and* identical centres — which varied module sizes make vanishingly rare. The
code was removed rather than kept as decoration.

Getting loops would mean steering placement to mate a module against two
existing doors at once. That is a change to level topology, not an
implementation detail — `docs/01-GAME-DESIGN.md` specifies "branches 4–6
dead-end rooms" — so it is flagged here rather than built.

## Level instantiation (M2-2 adapter)

`LevelService.build(seed)`, measured through the diagnostics bridge in a live
Play session:

```
seed 1: 17 modules (12 spine + 5 branches), 66880 studs^2, 149 parts, built in 5 ms
entrance: Junction_Cross at (0, 0)
pad Perimeter: 60 studs, 3 hops, opens at 180s
pad Processing: 236 studs, 9 hops, opens at 360s
pad Vault: 532 studs, 17 hops, opens at 540s
sealed check: 0 leaks over 17 modules
```

**The sealed check is the one worth keeping.** It fires a ray from every module
centre at head height toward each of its four faces and asserts something stops
it. A module whose unused connector was left as a hole, or whose doorway jamb
arithmetic was wrong, would leak — and the layout data would still look
perfectly valid, because the hole only exists in the geometry. 149 parts for 17
modules, built in 5 ms.

### Studio's require cache does not refresh on a Rojo sync

Requiring a module from the MCP bridge returns the version cached when it was
*first* required in that Studio session. Rojo updates a `ModuleScript`'s
`Source` in place, so the instance identity never changes and the cache never
misses. `Rooms.Source` contained the new `geometry` table while
`require(Rooms)` returned a table without it, and `LevelService` failed on a nil
index that did not exist on disk.

This is the companion to the M1 finding that the command bar has its own module
registry: that one is about *isolation*, this one is about *staleness*.

**Edit-mode verification of a freshly-synced module cannot be trusted.** Stop
and restart Play instead — the runtime loads a fresh registry at play start,
which is also closer to how the code actually runs.

Deleting the stale instance to force Rojo to re-create it **does not work**, and
leaves the tree broken: Rojo patches against its own view, so it believes the
instance still exists and every later update to that file silently goes
nowhere. Editing the file's contents does not bring it back either.

**Renaming the file does.** A rename reads as remove-then-add to the watcher, so
Rojo creates the instance fresh:

```powershell
Rename-Item src\shared\config\Rooms.luau _Rooms_tmp.luau
Rename-Item src\shared\config\_Rooms_tmp.luau Rooms.luau
```

That recovers a deleted instance without a plugin reconnect, and because the new
instance has a new identity it also clears the stale require cache — which makes
it the fix for the original staleness problem too, when restarting Play is not
an option.

## Enemy roster and nav pathing (M2-4)

`bridge:Invoke("rosterProbe", 5)` — one of each enemy spawned in a ring 70 studs
from the player, stepped by the live 20 Hz loop:

```
Skitter   SwarmNearest  state=attack dist 70.0 ->  4.0 (-66.0)  shielded=true
Sentry    Static        state=idle   dist 70.0 -> 70.0  (+0.0)
Hauler    PushObjective state=move   dist 70.0 -> 29.6 (-40.4)  speed=8.0
Lancer    KeepDistance  state=attack dist 70.0 -> 54.7 (-15.3)
Warden    ShieldNearby  state=move   dist 70.0 -> 22.4 (-47.6)  speed=10.0
Reclaimer HuntHeaviest  state=move   dist 70.0 -> 60.9  (-9.1)  speed=16.0
```

Each row matches its entry in `Enemies.luau`. The Sentry does not move a single
stud, the Lancer stops at 54.7 and attacks from range instead of closing, and
`shielded=true` on the Skitter is the Warden protecting it — the behaviour that
makes the Warden a priority target rather than just a big one.

`bridge:Invoke("navProbe", nil, 14)` — a Skitter spawned in the deepest room:

```
from: Vault_Core (module 9, Vault, hop 8)
distance 414 -> 124 (closed 290), stalled samples 0
  t= 1s dist= 394.3  moved +20.5  speed=22.0
  ...
  t=14s dist= 124.1  moved +19.9  speed=22.0
```

**290 studs closed through eight rooms with zero stalled samples**, holding full
speed throughout. This is the number that proves routing rather than steering:
`Steering.seek` is a straight line and the level is not convex, so without the
waypoint graph the entity would have pinned itself to the first wall and the
trace would read `moved +0.0` from t=1s onward. Reporting the per-second trace
rather than just the total is deliberate — "stuck on geometry" and "walking the
long way round" both look like slow progress in a summary.

Routes are cached per entity and rebuilt when either endpoint changes room,
which for a walking entity is a few A* calls per second across the whole
population rather than one per entity per tick.
